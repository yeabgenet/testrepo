1. Purpose, scope, and context

The manufacturer requires an event-driven integration that validates a Teamcenter assembly against release, engineering-change and cost rules; reports failures; and, when permitted, releases the end item and migrates it to Windchill. The solution also creates a digital thread and dashboard of integration outcomes.

In scope: Teamcenter event handling and assembly BOM inspection; three validation checks; Excel and email failure reporting; conditional release and migration; digital persistence; results dashboard.

Out of scope unless subsequently approved: arbitrary engineering change management; source master-data cleansing; continuous real-time bidirectional synchronization; expanded Windchill scope beyond the approved migration mapping.

2. Terms and definitions

Term

Definition

Item

Stable identity for a managed engineering object in Teamcenter.

ItemRevision

A specific revision of an Item; carries revision-specific lifecycle information.

Assembly

An ItemRevision that owns or resolves a BOM structure; need not be a separate table.

BOM

Bill of Materials; the selected component structure for the assembly.

Leaf Part

A component with no child BOM lines in the evaluated structure.

ECN

Engineering Change Notice. For this exercise, “open” means it has no release status.

Digital Persistence

Persistent representation of objects and relations used for the digital thread.

Run

A tracked invocation of the integration for an assembly/revision event.

3. High-level operational sequence

1. Teamcenter release-related event initiates a tracked integration run.

2. eQube resolves the selected assembly and its configured, multi-level BOM.

3. Three checks evaluate child release states, open ECNs, and leaf Part cost existence.

4. If any check fails, an Excel report is generated and emailed; ordinary release/migration is blocked.

5. If every check passes, the release action (if needed and authorized) completes, followed by Windchill migration.

6. The run reconciles target results and persists cross-system links; the dashboard exposes outcomes.

Design conflict requiring resolution: Slide #1 says “on release” and also instructs the process to “release it in TC” after validation. A pre-release workflow event is recommended, but the trigger is TBD until confirmed.

4. Functional requirements

ID

Requirement statement

Basis / verification criterion

AR-001

Release event handling: The integration system shall initiate a validation run for each qualifying Teamcenter assembly release event, using the assembly ItemRevision identity and event identifier.

Slide 1; Slide 2
Verify: A qualifying event initiates a tracked run for the specified assembly ItemRevision.

AR-002

BOM retrieval: The integration system shall retrieve the configured BOM structure for the triggering assembly ItemRevision, including all nested levels.

Slide 1
Verify: The run obtains a complete occurrence hierarchy under the agreed revision/configuration rule.

AR-003

Child release validation: The integration system shall evaluate the release status of every ItemRevision in the resolved assembly BOM other than the top-level end item.

Slide 1
Verify: An unreleased nested component is identified; the top-level ItemRevision is excluded from this check.

AR-004

ECN validation: The integration system shall identify ECNs associated with Parts in the resolved BOM and flag any ECN that has no release status.

Slide 1
Verify: An ECN with no release status produces a failed result; an ECN with a release status does not fail this rule.

AR-005

Leaf cost validation: The integration system shall verify the existence of a cost record in the relational cost source for every leaf-level Part in the resolved BOM.

Slide 1
Verify: A leaf Part with no matching cost record is flagged; the matching key and cost validity rule are documented.

AR-006

Overall validation: The integration system shall mark an assembly eligible for the normal release/migration path only when all three validation checks pass.

Slide 1
Verify: Three passes result in eligible; any failure results in a failed-validation outcome.

AR-007

Failure report: For every failed validation run, the integration system shall generate an Excel workbook identifying the assembly, evaluated checks, failed objects, and reasons.

Slide 1
Verify: Workbook is generated, opens correctly, and lists every recorded validation failure.

AR-008

Failure notification: For every failed validation run, the integration system shall email the Excel failure report to the designated recipient.

Slide 1
Verify: An email with the Excel failure report attached is sent to the designated recipient.

AR-009

Teamcenter release: When the assembly passes validation and is not yet released, the integration system shall perform the authorized Teamcenter release action defined for the workflow.

Slide 1; trigger ambiguity
Verify: The intended Teamcenter ItemRevision reaches the agreed target release status after the authorized workflow action.

AR-010

Windchill migration: After successful validation and the required Teamcenter release state, the integration system shall migrate the approved assembly scope to Windchill.

Slide 1
Verify: Required target objects and their BOM relationships can be reconciled to the source under the agreed scope.

AR-011

Cross-system digital thread: Following the integration run, the integration system shall persist relationships among corresponding Teamcenter, relational cost, and Windchill entities.

Slide 1
Verify: A stored cross-system relationship can be queried from a known source ItemRevision to its cost and Windchill counterpart.

AR-012

Results dashboard: The solution shall provide a dashboard of validation, release, migration, and execution outcomes for processed assemblies.

Slide 1
Verify: A reviewer can identify a run, its three check results, and migration outcome.

AR-013

Optional manual override: If exactly two of the three validation checks fail, the solution may support an authorized email-based override prior to release and migration. This feature shall remain disabled until approval rules are defined.

Slide 1 optional
Verify: When enabled, only the specified two-failure case is eligible and approval is required.

7. Validation rules and decision table

Fail condition

ECN

No ECN associated with a BOM Part is without release status

At least one associated ECN has no release status

Every leaf-level Part has an eligible relational cost record

One or more leaf Parts lack eligible cost
